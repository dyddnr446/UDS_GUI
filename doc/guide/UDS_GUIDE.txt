================================================================================
  UDS 간단 입문 가이드
================================================================================

□ 이 문서
- UDS가 무엇이고 왜 쓰이며, 로그 HEX를 어떻게 읽는지 짧게 정리한다
- 서비스·코드 전체 목록은 기준정보/uds_system_catalog.xlsx (+ doc/guide/uds_guide_catalog.xlsx) 를 본다


================================================================================
1. UDS가 왜 생겼나
================================================================================

□ 자동차에는 엔진·브레이크·바디 등 여러 ECU가 있다
- 공장·정비소·개발자는 ECU에 고장 조회, 값 읽기/쓰기 같은 진단을 걸어야 한다

□ 예전에는 제조사·ECU마다 진단 명령 코드와 의미가 제각각이었다
- 같은 “고장 목록 읽기”라도 회사마다 바이트가 달랐다
- 공구·소프트웨어·문서가 서로 호환되지 않았다
ㆍ협력사가 ECU를 납품할 때마다 OEM 전용 스펙을 새로 맞춰야 했다

□ 그래서 진단 “서비스”의 이름·번호·요청/응답 형태를 맞추는 표준이 필요해졌다
- 그것이 UDS(Unified Diagnostic Services, 주로 ISO 14229)다
- 테스터와 ECU가 같은 SID 의미로 말하게 하려는 공통 언어에 가깝다
ㆍ전송 매체는 CAN, DoIP 등일 수 있고, UDS는 그 위에서 “무슨 일을 할지”를 정한다
ㆍ예: 어디서나 0x22 ≈ DID로 데이터 읽기, 0x19 ≈ DTC 읽기, 거절은 7F + NRC


================================================================================
2. UDS란
================================================================================

□ UDS는 테스터와 ECU가 SID(서비스 ID)로 “할 일”을 주고받는 진단 대화 규칙이다 이름이다
- 세션 전환, 데이터 읽기/쓰기, 고장 코드 조회, 루틴 실행, 보안 접근 등을
  서로 다른 차·ECU에서도 비슷한 방식으로 다루려고 쓴다
ㆍ예: 22 F1 90 → “DID 0xF190(흔히 VIN) 값을 읽어 줘”


================================================================================
3. 요청과 응답
================================================================================

□ 요청 — 테스터가 ECU에게 보낸다
- 맨 앞 바이트가 SID이다
ㆍ예: 10 03, 22 F1 90, 19 02 FF

□ 긍정응답 — ECU가 요청을 받아들인 답
- 응답 SID는 보통 요청 SID + 0x40
ㆍ예: 22 … → 62 … / 10 03 → 50 03 …

□ 부정응답 — ECU가 거절한 답 (형식 이름: Negative Response)
- 항상 7F 로 시작하고, 둘째는 원래 요청 SID, 셋째는 NRC(거절 이유)
- 7F 자체는 새 서비스 요청이 아니라 거절 통지다
ㆍ예: 7F 22 31 → 0x22 요청이 NRC 0x31 으로 거절됨


================================================================================
4. 자주 만나는 SID
================================================================================

□ 0x10 DiagnosticSessionControl (세션 제어)
- ECU의 진단 세션(허용 기능 묶음)을 바꾼다
- 기본 세션에서 막힌 쓰기·시험·일부 DID를 열 때 먼저 맞춘다
ㆍ예: 10 03 → extended, 성공 시 50 03 …

□ 0x22 ReadDataByIdentifier (DID로 데이터 읽기)
- DID(데이터 식별자)로 ECU 안 “이름 붙은” 값을 읽는다
- 물리 주소를 몰라도 VIN·버전·센서값 등을 약속된 ID로 읽을 수 있다
ㆍ예: 22 F1 90 → 62 F1 90 + 데이터

□ 0x19 ReadDTCInformation (고장 코드 읽기)
- 저장된 DTC와 관련 정보를 조회한다
- 정비·디버깅에서 “뭐가 고장으로 잡혔는지”를 볼 때 출발점이 된다
ㆍ예: 19 02 FF → 마스크에 맞는 DTC 목록

□ 0x3E TesterPresent (테스터 생존 알림)
- 테스터가 아직 붙어 있음을 알려 세션을 유지한다
- 안 보내면 타임아웃으로 기본 세션으로 돌아가 이후 요청이 거절될 수 있다
ㆍ예: 3E 80 (응답 생략 형태가 흔함)

□ 0x7F NegativeResponse (부정응답)
- 특정 “할 일” SID가 아니라 거절을 알리는 응답 형식이다
- 로그에서 실패 원인을 NRC로 풀 때 가장 먼저 본다
ㆍ예: 7F 10 22 → 세션 전환(0x10)이 NRC 0x22 등으로 거절


================================================================================
5. 서브펑션
================================================================================

□ 서브펑션 — 같은 SID 안의 세부 동작
- 많은 서비스에서 요청의 둘째 바이트가 이 역할을 한다
- 10만으로는 부족하고, 03이면 extended / 01이면 default처럼 모드를 고른다
ㆍ예: 10 03 의 03, 19 02 의 02

□ suppress — 서브펑션 바이트의 bit7
- 켜면 문법상 긍정응답을 생략할 수 있다
- 하트비트처럼 응답이 불필요할 때 부하를 줄이려고 쓴다
ㆍ예: 3E 80 = 서브 0x00 + suppress

□ 참고
- 일부 서비스의 둘째 바이트는 서브펑션이 아니라 전송 모드·IO 파라미터 등이다
  (0x2A, 0x2F, 0x38 등). 상세는 카탈로그 has_subfunction / sub_byte_offset


================================================================================
6. HEX 로그를 읽는 순서
================================================================================

□ 한 줄 HEX를 사람 말로 바꿀 때
- 첫 바이트가 7F 인가?
  ㆍ맞으면 부정응답 → NRC(셋째 바이트)를 본다
- 아니면 Services에서 SID를 찾는다
  ㆍ긍정응답이면 SID − 0x40 이 원래 요청이다
- 세부 동작이 있으면 SubFunctions를 본다
- 바이트 배치가 필요하면 RequestLayout / ResponseLayout을 본다
ㆍ예: 7F 22 31 → NRC 0x31 → 없는 DID·범위 쪽을 점검
