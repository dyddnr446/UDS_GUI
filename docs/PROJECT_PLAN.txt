1. 프로젝트 개요
================================================================================

□ 프로젝트명
- 영문: UDS Diagnostic GUI & AI Advisor
- 한글: UDS 진단 GUI·AI 점검 조언기

□ 한 줄 정의
- JavaFX GUI가 Excel에서 제어기·DID를 로드하고 Extended Session(0x10)과
  교육용 SecurityAccess(0x27)를 통과한 뒤 ReadData(0x22)·WriteData(0x2E)를
  수행하며, 민감정보가 제거된 결과를 저장·AI 설명하는 진단 보조 도구이다.

□ 제품 입력·범위
- 입력은 완성 UDS HEX 로그, Excel 카탈로그, Access/Read/Write 입력과 세 CSV fixture이다.
- 현재 교환 구현은 상태형 FixtureEcuSimulator를 사용하는 FileDiagnosticExchangePort이다.
- RecordingDiagnosticExchangePort가 선택된 Port를 감싸 공통 저장·0x27 제거 정책을 적용한다.
- 실제 Socket/CAN/UART/ISO-TP는 범위 밖이며, 향후 transport lifecycle과
  controller adapter를 추가하면서 delegate Port를 교체한다.
- WriteData는 Must이다. 0x2E를 생성·저장하고 0x6E/0x7F 더미 응답을 분석하지만
  실제 ECU 상태는 변경하지 않는다.

□ 로그 파일 형식 (FR-01 계약)
- 인코딩: UTF-8
- 1행 헤더: ts,direction,hex
- 본문 한 줄: 시각,방향,HEX  (예: 1.200,REQ,22 F1 90)
- # 으로 시작하는 줄·빈 줄은 무시. 깨진 줄은 줄번호와 사유만 남기고 계속한다.
- 레퍼런스: samples/demo_session.log

□ 개발·검증 환경
- JavaFX GUI에서 컨트롤러 프로필과 더미 프레임 시나리오를 선택한다.
- Read 데이터셋은 0x62/0x7F/DID 불일치/짧은 프레임을 포함한다.
- Write 데이터셋은 0x6E/0x7F/DID 불일치/짧은 프레임/입력 검증 실패를 포함한다.
- 하위 통신·무응답·재시도·통신 타임아웃은 현재 구현하지 않는다.
- 시연·회귀용 레퍼런스 로그: samples/demo_session.log
- ReadData 시연 데이터: samples/read_data_scenarios.csv
- WriteData 시연 데이터: samples/write_data_scenarios.csv
- Access 시연 데이터: samples/access_scenarios.csv
- 수업용 평문 credential: config/demo_password.txt
- AI 해석은 외부 AI API를 사용하며 API가 실패해도 사실 해석·Finding은 유지한다.

2. 추진 배경과 목표
================================================================================

□ 배경
- 동아리 임베디드 실습·벤치에서 UDS 통신 결과는 HEX 나열로 남는 경우가 많다.
- SID·서브펑션·NRC를 매번 수동으로 찾는 비용이 크고, 신입 팀원 인수가 어렵다.
- “모터가 돌다 갑자기 멈췄다”처럼 현상은 말하지만, 다음에 어떤 진단 요청을
  날려야 하는지로 연결되지 않는 경우가 많다.

□ 목표
- HEX 로그를 사람이 읽는 서비스·오류 의미로 자동 변환한다.
- JavaFX GUI에서 Interpreter·ReadData·WriteData·AI Advisor를 한 도구로 제공한다.
- Excel 기반 profile/DID 선택과 Access 탭의 Extended·unlock 흐름을 제공한다.
- 현상·해석 결과·더미 DID 값을 외부 AI가 설명하고 점검 체크리스트를 제시한다.
- JAVA 수업에서 GUI, 파싱, 모듈 분리, 표 기반 데이터, 외부 API 연동을 실증한다.

□ 비목표 (제외 범위)
- 실차 CAN 버스 직접 접속 및 ISO-TP 재조립
- Socket/CAN/UART 등 실제 하위 통신 구현과 ECU 직접 송수신
- 실제 OEM seed/key 알고리즘과 production credential 저장
- OEM 보안 키 알고리즘 구현
- 모터·액추에이터를 프로그램이 직접 구동·정지시키는 제어 기능
- LLM이 SID/NRC 사실을 추측하거나 고장 부위를 단정하는 구성
- 팀 문서 기반 RAG/벡터 DB (현재 Knowledge 문서가 없으므로 제외)

4. 해결할 문제와 기대 효과
================================================================================

□ 해결할 문제
- HEX만으로는 통신 의미를 즉시 파악하기 어렵다.
- 부정응답이 쌓여도 “어디부터 볼지” 우선순위가 없다.
- 현상(예: 모터 급정지)과 UDS 재요청(특히 0x22 읽기) 사이가 끊겨 있다.
- CAN/TP까지 넣으면 수업 시연이 장비 변수에 흔들린다.

□ 기대 효과
- 동일 로그를 동일하게 해석·재현할 수 있다.
- AI Advisor 설명으로 UDS 진입 장벽을 낮춘다.
- ReadData 탭에서 “다음에 무엇을 읽을지”와 반환값 의미를 함께 본다.
- 보드 없이도 로그·더미 프레임만으로 GUI 시연 스토리를 완주할 수 있다.

□ 확장 경계
- 유지: GUI 계약, Catalog/Interpreter, AccessGuard, Read/Write 도메인,
  DiagnosticExchangePort 요청·응답 모델과 Recording Decorator
- 추가·교체: Recording Port의 delegate, 연결 수명·주소·timeout·0x78·session affinity,
  C Gateway의 FarDriver/VESC ControllerProtocolAdapter
- 따라서 “Port 클래스 하나만 교체”가 아니라 “도메인은 유지하고 transport lifecycle과
  제조사 adapter를 추가·교체”하는 구조이다.

□ 개발·검증 흐름
- 앱 시작 시 Excel을 검증해 profile/DID ComboBox를 생성한다.
- Access 탭에서 profile 선택 → Extended → PasswordField 인증을 수행한다.
- Guard 통과 후 Coordinator → Recording Port → File ECU 순으로 교환한다.
- Analysis Session 수명 동안 File/Recording/Simulator는 단일 인스턴스이며,
  시나리오 변경은 FileDiagnosticExchangePort.setFixtureRunConfig(...)만 사용한다.
  scenario_id는 FixtureRunConfig에만 두고 공통 교환 요청에는 넣지 않는다.
- 인증 전 Read/Write는 ACCESS_DENIED이며 프레임·JSONL을 만들지 않는다.
- ReadData 파서·Finding은 expected_value/expected_status와 1:1 대조
- WriteData 검증·인코더·WriteResult는 write fixture expected_status와 1:1 대조
- AI 실패 시에도 카탈로그 해석·값·Finding 화면 유지

7. 핵심 기능 계획
================================================================================

□ 기능 A. 로그 해석기 (Interpreter)
- 로그 파일 로드(FR-01 형식) 및 HEX 정규화·검증
- SID / 서브펑션 / 부정응답(0x7F+NRC) 자동 명명
- 서브펑션·suppress는 카탈로그 적용 SID에만 bit7 마스킹 (0x22 DID에는 적용 안 함)
- 시연 범위 SID의 주요 필드 분해
  ㆍ0x10, 0x11, 0x14, 0x19, 0x22, 0x27, 0x3E, 0x7F 및 대응 긍정응답
- 0x27/0x67의 seed·key 바이트는 표시·저장 시 <REDACTED>로 마스킹한다.
- JavaFX Interpreter 탭에 사실 결과를 AI 설명과 분리 출력

□ 기능 B. JavaFX UDS GUI
- 필수 탭: Access / Interpreter / ReadData / WriteData / AI Advisor /
  Analysis Session·Settings
- ControllerProfiles·DidProfileSupport·OemExtensions에서 profile/DID ComboBox 생성
- profile 변경·catalog reload 시 DID 선택과 접근 권한 초기화
- 외부 AI 호출은 백그라운드에서 수행하고 진행·취소 상태 표시

□ 기능 C. Diagnostic Access (Must)
- 명칭: DiagnosticAccessFacade, SessionControlService, SecurityAccessService
- 초기 상태 DEFAULT_LOCKED. 성공 조건은 byte0==0x50 && (byte1&0x7F)==0x03
  (검증된 50 03)일 때만 EXTENDED_LOCKED. 50 01은 SESSION_ECHO_MISMATCH로
  DEFAULT_LOCKED 유지.
- PasswordField 입력과 27 01/67 01 seed, 교육용 HMAC key, 27 02/67 02 성공 시
  EXTENDED_UNLOCKED
- 비밀번호는 config/demo_password.txt와 File ECU simulator가 검증하며 raw 비밀번호를
  UDS 프레임에 싣지 않는다.
- profile/reload/Port 변경·Analysis Session 복원 시 DEFAULT_LOCKED
- Guard는 unlock과 DID metadata가 모두 맞을 때만 Read/Write 요청 생성을 허용
- resultingState 포함 AccessEvidence는 Context 전이 후
  SafeExchangeRecorder.recordAccessEvidence(...)로 기록한다.

□ 기능 D. AI Advisor (Must)
- 사용자가 현상을 짧은 문장으로 입력한다.
- 대표 예시
  ㆍ“모터가 동작 중에 갑자기 정지했는데, 왜 문제가 생겼는지 알고 싶다.”
- SymptomDidMap으로 현상→확인 DID 후보를 제안하고, 실행은 runtime_enabled=Y만
  (ND: 0x1001,0x1002,0x1007 / Flipsky: 0x1001). 0xF186은 정적 로그 참고만.
- DecodeResult·ParsedDidValue·Finding·WriteResult·AccessEvidence를 sanitizer로 구조화
- 외부 AI API가 관측값 기반 설명·확인 목록 생성
- AI 결과는 별도 라벨과 근거 ID를 표시하고 카탈로그 사실을 덮어쓰지 않음
- AI 오류·오프라인이면 사실 해석·Finding 중심 화면과 경고 유지

□ 기능 E. File Port 기반 ReadDataByIdentifier(0x22)
- GUI에서 fixture scenario_id를 선택하면 기존 File Port에
  setFixtureRunConfig(...)로만 주입하고, 서비스에는 profile·DID만 전달
- DID 선택 → 0x22 요청 생성
- Recording Port → File Port → 상태형 simulator → 응답 → 공통 안전 기록
- 실제 네트워크·CAN 송신·재시도·통신 타임아웃 없음
- 정적 로그의 0x62도 동일 DidValueParser로 처리(runtime_enabled 무관)
- OemExtensions(data_type·scale·unit·normal_min/max)로 표시·Finding
- BigDecimal 표시 자릿수 = scale 소수 자릿수
- Read status enum(CSV 1:1): NORMAL|ABNORMAL|REJECTED|PARSE_ERROR_*
  normal_min/max 없으면 RANGE_NOT_APPLICABLE
- 같은 scenario_id는 같은 값·Finding을 반환

□ 기능 F. File Port 기반 WriteDataByIdentifier(0x2E)
- GUI에서 fixture scenario_id를 setFixtureRunConfig로 주입한 뒤
  프로필·Write DID·값을 검증한다.
- 카탈로그 scale과 byte_length에 따라 바이트를 인코딩하고 0x2E 요청을 만든다.
- File Port가 fixture의 0x6E/0x7F 응답을 반환하고 Recording Port가 저장한다.
- Write status enum(CSV 1:1): ACCEPTED|REJECTED|VALIDATION_ERROR_*|PARSE_ERROR_*
- WD-ERR-004/005 등 Validator 차단은 Port를 호출하지 않는다.
- 결과는 요청 산출물에 대한 상태이며 실제 ECU 변경 성공을 의미하지 않는다.

□ 기능 G. 최종 체크리스트·Analysis Session
- 결정론적 Finding·WriteResult·AccessEvidence와 AI 설명을 구분해 조립
- 각 AI 항목에 로그/DID/Finding/WriteResult/AccessEvidence 근거 ID ≥1
- 0x27 payload를 제거한 결과를 Analysis Session 파일로 기록

8.6 대표 흐름 · 상태 변경 · 거절 시 유지 상태
--------------------------------------------------------------------------------

□ 시작 상태
- JDK 17 + Maven + JavaFX로 실행한다.
- Apache POI로 catalog schema v2를 검증하고 불변 snapshot을 만든다.
- 세 Access/Read/Write fixture와 credential 파일을 검증한다.
- ActiveDiagnosticContext는 profile 미선택·DEFAULT_LOCKED·새 generation으로 시작한다.
- API 키는 UDS_AI_API_KEY 환경변수에서만 읽고 파일·화면·로그에 저장하지 않는다.

□ Access 대표 흐름
1. Access 탭의 ControllerProfiles ComboBox에서 profile을 선택한다.
2. profile 변경은 generation을 증가시키고 DID 선택·권한을 DEFAULT_LOCKED로 초기화한다.
3. 10 03 → byte0==0x50 && (byte1&0x7F)==0x03 에서만 EXTENDED_LOCKED
   (50 01 → SESSION_ECHO_MISMATCH, DEFAULT_LOCKED 유지)
4. 27 01 → 67 01 seed. fixture <SEED> 치환 값은 고정 AA BB CC DD
5. PasswordField 값을 즉시 char[]로 복사하고 control을 비운다.
6. HMAC-SHA256(password, seed||00||profileId UTF-8)의 앞 4바이트로 27 02 전송
   (<KEY>는 27 02+4바이트 길이 매칭, 실제 일치는 HMAC 상수시간 비교)
7. File ECU는 config/demo_password.txt로 기대 key를 계산·상수 시간 비교한다.
   NEGATIVE fixture(ACCESS-INVALID-KEY 등)는 CSV response_kind를 우선한다.
8. 67 02이면 EXTENDED_UNLOCKED, 7F 27 35이면 EXTENDED_LOCKED 유지
9. password 배열은 finally에서 지운다. Recording Port는 0x27 raw 즉시 폐기.
   Context 전이 후 SessionControl/SecurityAccess가
   SafeExchangeRecorder.recordAccessEvidence(...)를 호출한다.

□ ReadData 대표 흐름
1. 입력: GUI가 profile, did, scenarioId를 받는다.
2. GUI 구성 계층: 기존 File Port에 setFixtureRunConfig(scenarioId)만 호출한다.
3. Guard가 EXTENDED_UNLOCKED·profile·DID metadata를 검증한다.
4. 거절이면 ACCESS_DENIED만 반환하고 요청 프레임·JSONL을 만들지 않는다.
5. 허용이면 22 [DID_H] [DID_L] → Recording Port → File ECU
6. Recorder가 requests/responses JSONL을 append+flush한다.
7. Parser/Analyzer가 ParsedDidValue와 Finding을 만든다.
   status는 CSV expected_status와 1:1(NORMAL|ABNORMAL|REJECTED|PARSE_ERROR_*).
   normal_min/max 없으면 RANGE_NOT_APPLICABLE. BigDecimal 표시 자릿수=scale.
8. ReadDataViewModel이 결과를 표시하고 AnalysisSessionStore에 append한다.
- 0x7F/파싱 거절: 오류 ReadDataResult만 append하며 직전 성공 값은 덮어쓰지 않는다.

□ WriteData 대표 흐름
1. 입력: GUI가 profile, writeDid, logicalValue, scenarioId를 받는다.
2. GUI 구성 계층은 기존 File Port에 setFixtureRunConfig(scenarioId)만 호출한다.
3. Guard가 접근 권한을 검증하고 Validator가 type/range를 확인한다.
4. Validator 실패(WD-ERR-004/005): Port 미호출, VALIDATION_ERROR_*만 기록.
5. 검증 성공 시 Encoder → Generator → Recording Port → File ECU 순으로 교환한다.
6. Parser가 0x6E echo DID 또는 0x7F NRC를 WriteResult로 만든다.
   status는 CSV 1:1(ACCEPTED|REJECTED|VALIDATION_ERROR_*|PARSE_ERROR_*).
7. WriteDataViewModel이 표시하고 AnalysisSessionStore에 append한다.
- 0x7F/echo 불일치/짧은 응답: 실패 결과를 기록하되 이전 ACCEPTED 결과와 입력칸은 유지한다.
- ACCEPTED는 fixture 교환 성공이지 실제 ECU 상태 변경 성공이 아니다.

□ AI 대표 흐름
1. 입력: 현상 + DecodeResult·ParsedDidValue·Finding·WriteResult·AccessEvidence
2. Sanitizer가 0x27 payload·password·seed·key를 제거한다.
3. Advisor가 evidenceIds를 붙여 OpenAI-compatible provider에 JSON Schema로 요청
4. 검증된 응답만 AiAdviceResult로 저장
- AI 실패/취소: AiError만 추가하며 결정론적 결과와 직전 정상 AI 결과를 삭제하지 않는다.

□ 저장·복원
- 모든 파일은 schemaVersion=1과 analysisSessionId를 가진다.
- catalogVersion은 Analysis Session 시작 시 로드한 uds_catalog.xlsx SHA-256이다.
- requests/responses.jsonl …… 일반 0x10/0x22/0x2E 교환 raw; 0x27 payload 저장 금지
- access-evidence.jsonl …… operation·NRC·resultingState·payloadRedacted=true
- analysis.json …… DecodeResult·Finding·WriteResult·AccessEvidence·AI와 evidenceIds
- analysis-session.json …… catalogVersion·설정·커밋 recordId 참조
- JSONL은 한 행 append 후 flush하고 analysis-session.json은 임시 파일→원자 교체한다.
- 저장 실패 시 메모리 결과를 유지하고 PersistenceError를 표시하며 가짜 응답을 만들지 않는다.
- 복원 시 analysis-session.json이 참조한 커밋 ID만 읽는다. 누락 파일·schemaVersion·
  catalogVersion 불일치는 가능한 항목만 읽기 전용 복원하고 경고한다.
- 복원된 과거 UNLOCKED 표시는 권한으로 사용하지 않고 runtime은 DEFAULT_LOCKED이다.
- API 키·password·seed·key는 어느 파일에도 저장하지 않는다.

□ 시나리오 4. 동아리 인수
- 시작: 송신자가 분석을 마친 analysisSessionId를 선택하고 폴더를 전달한다.
- 입력: outputs/<analysisSessionId>/의 analysis-session.json·analysis.json·JSONL
- 전달 데이터: schema/catalog 버전, 컨트롤러 프로필, 요청·응답, DecodeResult,
  Finding, WriteResult, AI 결과와 evidenceIds
- 수신자 행동: JavaFX Analysis Session 탭에서 읽기 전용으로 복원한다.
- 성공 결과: 송신자와 같은 결정론적 사실 결과를 보고 AI 항목에서 원본 근거 ID를 추적한다.
- 실패 결과: 파일 누락·schema/catalog 버전 불일치를 경고하고 복원 가능한 결과만 표시한다.
- 상태 변경: 과거 권한은 복원하지 않고 DEFAULT_LOCKED. 재저장 시 새 analysisSessionId

□ 시나리오 5. 도착 프레임 AI 분석 (UC-04)
- 정적 로그 또는 더미 데이터의 0x62/7F를 동일 파서로 값·Finding/오류화한다.
- 사실 결과를 AdvisorContext에 넣어 AI 설명을 요청한다.

□ 시나리오 6. WriteData 산출물 생성·분석 (UC-05)
- 시작: 프로필과 0x2001~0x2006 중 지원 DID를 고르고 값을 입력한다.
- 선행: UC-06으로 EXTENDED_UNLOCKED
- 요청: Guard → 검증·인코딩 → 0x2E → Recording Port → File ECU
- 결과: CSV expected_status 1:1(ACCEPTED|REJECTED|VALIDATION_ERROR_*|PARSE_ERROR_*).
  Validator-only 오류는 Port를 호출하지 않는다.
- 거절되어도 이전 결과를 덮어쓰지 않으며 실제 모터 상태는 바뀌지 않는다.

□ 기능

- WriteData 입력 오류는 요청을 만들지 않고, 거절은 이전 성공 상태를 보존
- output·AI context에 password·seed·key byte sequence 0건

□ 시연·검증 환경
- 하드웨어 없이 레퍼런스 로그·CSV 더미 프레임으로 스토리 완주
- GUI에서 사실 해석 / 값·Finding / AI 설명 / 체크리스트 구분

- 0x36/37 카운터·Clock·실제 timeout·TesterPresent·Socket/CAN은 후속

□ 증상–DID 매핑 부재
- 교육용 DID를 OemExtensions에 명시, 없으면 “매핑 필요” 표시
- 급정지 실행 DID: ND=0x1001,0x1002,0x1007 / Flipsky=0x1001 (0xF186 정적 참고)

□ 실차 안전
- 상태형 File ECU만 사용. 0x2E 결과는 fixture이며 실차 제어 경로 없음

□ 평문 credential
- 수업 fixture임을 UI/README에 표시하고 CredentialStore 뒤에 격리
- 끝단 CRLF/LF만 제거. BOM·빈 값·다중 행·길이 오류를 거절하며 로그·AI에 미저장

□ 외부 AI 장애·정보 노출
- AI 오류 시 결정론적 결과 유지. API 키·password·seed·key 미저장
- Interpreter가 정적 로그 0x27/0x67을 <REDACTED>, Sanitizer가 AI context에서도 제거

□ 시연 데이터 오류
- 더미 CSV의 DID·요청·응답·expected_status를 카탈로그와 자동 대조
- RPM/ERPM을 speedBasis로 구분하고 pole count·기어비 전에는 차량 속도를 계산하지 않음

================================================================================
부록 C. 교육용 seed/key 계약
================================================================================

□ 알고리즘
- HMAC-SHA256(key = UTF-8(password), message = seedBytes || 0x00 || UTF-8(profileId))
- 교육용 key = digest[0..3] (앞 4바이트, 전송 순서 그대로)
- File ECU는 같은 알고리즘으로 기대 key를 계산하고 상수 시간 비교한다.

□ fixture 치환 규격 (samples/access_scenarios.csv)
- <SEED> → 고정 바이트 AA BB CC DD
- <KEY> → 요청 템플릿에서 27 02 + 4바이트 길이만 매칭. 실제 일치 여부는 HMAC 상수시간 비교
- response_kind=NEGATIVE인 행(ACCESS-INVALID-KEY 등)은 CSV kind/응답을 우선한다
- ACCESS-ATTEMPTS-EXCEEDED(0x36)·ACCESS-DELAY-ACTIVE(0x37)는 고정 부정 응답만 반환.
  attempt 카운터·Clock 연동은 후속 단계

□ 고정 테스트 벡터
- password = uds-demo-2026  (config/demo_password.txt; trailing CRLF/LF만 제거)
- seedBytes = AA BB CC DD
- profileId = FARDRIVER_ND72530
- message = AA BB CC DD 00 46 41 52 44 52 49 56 45 52 5F 4E 44 37 32 35 33 30
- HMAC-SHA256 digest 앞 4바이트 = D3 AC 3F 47  (재생성 스크립트/단위 테스트가 검증)
- ACCESS-VESC-SUCCESS 동일 seed/key 계약으로 unlock 후 RD-VESC-001 검증
- 이 값은 수업 fixture이며 OEM 보안 알고리즘이 아니다.

□ 결과 상태 enum (CSV expected_status 1:1)
- Read: NORMAL | ABNORMAL | REJECTED | PARSE_ERROR_*
  (범위 없음 Finding detail: RANGE_NOT_APPLICABLE; fixture 문자열과 충돌 없게 status+detailCode)
- Write: ACCEPTED | REJECTED | VALIDATION_ERROR_* | PARSE_ERROR_*
