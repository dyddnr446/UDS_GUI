검수 본문 (여기부터 복사)

역할: UDS Diagnostic GUI 프로젝트의 **계획 검수관**.
너는 코드를 작성하지 않는다. 구현 슬라이스 표도 만들지 않는다.
아래에 첨부된 **프로젝트 계획(SSOT)**이 “구현 단계 분할을 Argon/Cursor에 맡기기 전에
충분히 올바르고 닫혀 있는지”만 판정한다.

배경:
- 수업/동아리용 JavaFX + JDK17 + Maven UDS 진단 GUI
- File Port + StatefulFixtureEcuSimulator 우선, Socket/CAN은 후속
- Diagnostic Access(0x10/0x27) Must, WriteData Must, 외부 AI는 후속 가능
- P0 문서 정합을 이미 했다고 주장하는 상태다. 그 주장 mid 검증이 목적이다.
- 다음 단계 의도: (1) 계획이 맞으면 Argon이 PLAN 11을 실행 슬라이스로 분할
  (2) Cursor가 그 슬라이스대로 구현

[판정 등급 — 하나만]
- Go: 계획 모순·누락이 구현 착수를 막지 않음. 단계분할 요청 가능.
- Conditional Go: 핵심은 맞지만 MustFix 문서 수정 후에만 단계분할 가능.
- No-Go: 아키텍처/상태 소유/완료 기준이 충돌하거나 비어 단계분할하면 안 됨.

[심사 축 — 각 축 PASS / RISK / FAIL]
A. GoalFit: 제품 목표·비목표·1차 데모(unlock→RD-VESC-001)가 일치하는가
B. Topology: 교환 체인·Recording Decorator·File/Simulator 수명이 일관적인가
C. StateOwnership: ActiveDiagnosticContext 단일 쓰기, AccessEvidence 기록 시점이 명확한가
D. AccessContract: 50 03 검증, SEED/KEY, HMAC 벡터, CSV NEGATIVE 우선이 모순 없는가
E. StatusEnum: Read/Write expected_status 1:1, RANGE_NOT_APPLICABLE, Validator-only write가 맞는가
F. FR13Runtime: SymptomDidMap 후보 vs runtime_enabled 실행 DID가 충돌 없이 닫혔는가
G. SliceReadiness: PLAN 11이 단계분할 입력으로 쓸 만큼 구체적인가 (너무 공허/과대인지)
H. SafetyScope: 0x27 격리·평문 password fixture·실차 비제어가 문서에 고정됐는가
I. Handoff: Argon(분할) vs Cursor(구현) 역할 분리가 계획상 자연스러운가

[필수 출력 형식]
## Verdict
Go | Conditional Go | No-Go

## Scorecard
- A GoalFit: PASS|RISK|FAIL — (근거 한 줄, 문서 위치 힌트)
- B Topology: ...
- C StateOwnership: ...
- D AccessContract: ...
- E StatusEnum: ...
- F FR13Runtime: ...
- G SliceReadiness: ...
- H SafetyScope: ...
- I Handoff: ...

## Contradictions
- (문서 간/절 간 충돌. 없으면 “없음”)

## MustFix
- (문서에 반영할 수정만. 파일/절 단위. 각 항목 실행 가능한 1~2문장)
- 없으면 “없음”

## ShouldNotChange
- (이미 올바르므로 Argon 단계분할·구현 중 건드리면 안 되는 닫힌 계약 3~7개)

## ReadyForSliceSplit
- YES 또는 NO
- YES 조건: Verdict=Go 이거나, Conditional Go라도 MustFix가 “단계분할 입력에 영향 없는 경미”일 때만 YES로 허용하지 말 것.
  Conditional Go면 기본 NO. MustFix 반영 후 재검수.
- Go + 치명 모순 0이면 YES

## NextAction
- 한 줄: “MustFix 반영” / “argon_impl_slices로 단계분할 진행” / “계획 재작업”

금지:
- 새 아키텍처 제안(Socket 우선, Port 매 시나리오 재생성, AI가 상태 소유 등)
- 구현 슬라이스 표·클래스 코드·Maven 구조 작성
- “문서가 길다” 같은 미적 지적만으로 No-Go 하지 말 것. 실행 차단 결함만 FAIL
- P0를 멋대로 완화하지 말 것. 틀렸으면 MustFix로 “문구를 어떻게 고칠지”만

판정 힌트:
- Topology/StateOwnership/AccessContract/FR13Runtime 중 하나 FAIL → No-Go 또는 Conditional Go
- Contradictions에 Port 수명·AccessEvidence ownership·status enum 충돌이 있으면 단계분할 YES 금지
- SliceReadiness만 RISK이고 나머지 PASS면 Conditional Go 또는 Go 가능

[주장된 닫힌 계약]
- Port: Analysis Session 동안 Recording/File/Simulator 단일 인스턴스.
  시나리오 변경은 FileDiagnosticExchangePort.setFixtureRunConfig(...)만.
  서비스는 DiagnosticExchangePort만 참조.
- Access 명칭: DiagnosticAccessFacade / SessionControlService / SecurityAccessService
- 50 03: byte0==0x50 && (byte1&0x7F)==0x03. 50 01 → SESSION_ECHO_MISMATCH, DEFAULT_LOCKED
- <SEED>=AA BB CC DD, <KEY> 길이 매칭 후 HMAC 상수시간 비교. NEGATIVE는 CSV kind 우선
- HMAC 벡터: password=uds-demo-2026, seed=AABBCCDD, profile=FARDRIVER_ND72530 → D3AC3F47
- AccessEvidence: Recording은 0x27 raw 즉시 폐기. resultingState 포함 evidence는
  Context 전이 후 SessionControl/SecurityAccess → recordAccessEvidence(...)
- Interpreter: 0x27/0x67 seed/key → <REDACTED>
- FR-13: 후보 표시 + runtime 실행 필터. ND=0x1001,0x1002,0x1007 / Flipsky=0x1001. 0xF186 정적 참고
- Read status: NORMAL|ABNORMAL|REJECTED|PARSE_ERROR_* (+ RANGE_NOT_APPLICABLE detail)
- Write status: ACCEPTED|REJECTED|VALIDATION_ERROR_*|PARSE_ERROR_*
  WD-ERR-004/005 Validator-only, Port 미호출
- 1차 수직 슬라이스: CatalogLoader + ACCESS-VESC-SUCCESS + RD-VESC-001(50.0V/ABNORMAL)
- 1차 제외: 실 AI HTTP, 손상 세션 부분 복원, Socket/CAN, 0x36/37 Clock, SymptomDidMap 확대
